## STANDING RULES

These apply to every line of code you write, in every phase.

### Rule 1 — The architectural invariant

> **React must never re-render during gameplay.**

Concretely:

- No `setState` in any code path reached from `useFrame`.
- Per-frame HUD values (hull, heat, score) are written **directly to DOM refs**, bypassing React entirely.
- Event-driven state (screen, wave number, outpost status) goes through zustand at **≤10 Hz**.
- Simulation state lives in plain mutable objects and typed arrays. Never in `useState`, never in Context, never in zustand.

This is verified by an automated test (§37.6) that fails the build if any component re-renders during 10 seconds of gameplay. Write that test in Phase 1, before it can be violated.

### Rule 2 — Layer separation is lint-enforced

`src/game/**` **may not import** `react`, `three`, `@react-three/*`, or anything DOM-related.

Configure ESLint `no-restricted-imports` to enforce this in Phase 1. It is not a guideline; it is a build error.

This is what makes the entire simulation unit-testable in plain Node with no browser, and it is the structural guarantee behind Rule 1.

### Rule 3 — Zero allocation in the hot path

No `new`, no object literals, no array literals, no closures inside anything called every frame.

- Pre-allocate every pool at startup (§31.2).
- Use module-scoped scratch vectors and reuse them.
- Structure-of-arrays over typed arrays for entity data.
- Mark hot functions `/** @hot-path */` and keep them allocation-free.

**The target is zero heap growth during play** (§34.1), verified by a 5-minute soak test. The previous version leaked continuously because it allocated per-bullet and per-particle and never disposed anything — this is the specific failure being engineered out.

### Rule 4 — Dispose everything

Every geometry, material, texture, and render target is owned by a registry and disposed on teardown. Never call `scene.remove()` without disposing what you removed.

V1's total absence of disposal is documented in §2.2. Do not reproduce it.

### Rule 5 — Fixed timestep, always

All simulation runs at the fixed timestep in §18.2. **Nothing** in `src/game/` may read wall-clock time or frame delta directly.

Any per-frame smoothing must use the frame-rate-independent form from §21.4:

```ts
// WRONG — framerate dependent, this is V1's bug class
x += (target - x) * 0.05;

// RIGHT — exact at any dt
x = target + (x - target) * Math.exp(-lambda * dt);
```

If you find yourself writing a bare multiplier against a delta, stop and check which form you need.

### Rule 6 — Dependencies must be justified

The approved stack is §28.2. The justifications are §29.

**Do not install anything not on that list without asking first.** When you propose one, state: what breaks without it, what it costs in bundle size, what the alternatives are, and whether it should be mandatory or optional.

Removing a dependency by inlining the small part you use is usually the better trade. §29 explicitly flags `drei` as a candidate for this if it causes React 19 friction (risk R1).

### Rule 7 — TypeScript, strictly

- `strict: true`, plus `noUncheckedIndexedAccess`, `noImplicitOverride`, `exactOptionalPropertyTypes`.
- **No `any`.** If a type is genuinely unknown, use `unknown` and narrow it.
- **No non-null assertions (`!`)** except immediately after an explicit check you can point to.
- No `@ts-ignore`. `@ts-expect-error` only with a comment explaining why, and only for known upstream type bugs.
- Prefer `type` for unions and `interface` for object shapes that may be extended.
- Discriminated unions for state machines — game state, weapon state, and outpost state should all be impossible to represent incorrectly.

Zero TypeScript errors is an acceptance criterion (§42), not an aspiration.

### Rule 8 — Naming

- Use the **exact terminology from `gameplan.md`** in code: `Harvester`, `Interceptor`, `Sentinel`, `Outpost`, `ThreatRing`, `Playing`, `Debrief`, `WaveClear`. Do not invent synonyms. If the spec says `Outpost`, never write `Base` or `Station`.
- Systems end in `System`. Entities are singular nouns. Booleans read as predicates (`isDraining`, `hasLock`).
- Constants in `SCREAMING_SNAKE_CASE`, all in `src/game/data/constants.ts` — **one file for every tuning value** so game feel can be tuned in one place.
- Files match their default export.

### Rule 9 — Component boundaries

- `src/game/` — pure simulation. No framework imports. Fully unit-testable in Node.
- `src/render/` — R3F. May *read* game state. **Never mutates it.**
- `src/ui/` — React screens and HUD. Reads via stores and refs. Never touches the simulation directly.
- `src/state/` — zustand stores and persistence only.

One boundary crossing exists: the render bridge (§31.3), which writes interpolated transforms into instanced-mesh buffers. That is the **only** place simulation meets Three.js. Keep it that way — when something desyncs, there should be exactly one place to look.

### Rule 10 — Error handling

- React error boundaries per screen. A HUD component failing must never take down the game.
- Handle WebGL context loss with automatic recovery and a clear message (§38.5).
- Validate everything read from `localStorage` against a schema. Corrupt data resets to defaults with a toast — it must **never** prevent someone from playing.
- Never swallow an error silently. If you catch it, either handle it meaningfully or log it with enough context to debug.
- No `console.log` in production code. A dev-only debug logger, stripped at build.

### Rule 11 — Performance is verified, not assumed

Every performance claim is measured:

- Profile before optimising. Report the actual numbers.
- Check draw calls with `renderer.info.render.calls` against the ≤120 budget.
- Watch heap growth in DevTools over a 5-minute session.
- Build the dev perf overlay (§34.3) early, in Phase 2 — you will use it constantly.

**Never claim a performance target is met without showing the measurement.**

### Rule 12 — Testing

Write tests alongside the code, not after.

- Every pure function in `src/game/physics/` and `src/game/math/` gets unit tests.
- Every bug you fix gets a regression test first — **write the failing test, then fix it.**
- The specific regression tests from §37 are mandatory, particularly:
  - **Framerate independence:** identical simulation state after 10 s at 60/120/144 Hz.
  - **No tunneling:** projectiles at up to 400 u/s always register hits.
  - **Zero heap growth:** 5-minute soak, growth < 5 MB.
  - **Zero React re-renders** during 10 s of Playing.
- Target ≥85% coverage on `src/game/`. Do not chase UI coverage — E2E serves that better.

### Rule 13 — Debugging method

When something breaks:

1. **Reproduce it reliably.** The seeded PRNG (§10.4) makes this possible — use the seed.
2. Form a hypothesis and state it.
3. Test the hypothesis with a minimal change or a log.
4. Fix the actual cause, not the symptom.
5. Add a regression test.
6. Verify the fix and check you have not broken anything adjacent.

**Do not stack speculative fixes.** If two changes go in and the bug disappears, you do not know which one worked, and you have probably left a bug behind. Revert and isolate.

If you are stuck after three genuine attempts, stop and tell me what you have tried, what you have ruled out, and what you think is happening.

### Rule 14 — Git

- Branch per phase: `phase-2-core-prototype`.
- Small, focused, atomic commits. One logical change each.
- Present tense, imperative: `Add swept-sphere collision detection`.
- Reference the spec section: `Implement radial gravity field (gameplan §22.2)`.
- Never commit broken code to `main`.
- **Never commit or push unless I ask you to.**

### Rule 15 — Documentation

- JSDoc on every exported function in `src/game/`, with the equation and the `gameplan.md` section it implements.
- Comment the **why**, never the what. `// Re-orthonormalise: float drift skews the basis visibly within ~60s` is useful. `// normalize the vector` is noise.
- Match the surrounding code's comment density. Do not over-annotate.
- Keep `README.md` current with setup, architecture, and the maths that matters. Judges read it.

### Rule 16 — Refactoring

- Refactor when code is *wrong*, unclear, or blocking work. Not for taste.
- Never mix a refactor with a behaviour change in one commit.
- Have the tests green before you start and green after you finish.
- **Do not rewrite working code you merely dislike.** If UI Builder produced a component that works, is readable, and meets the spec, keep it.

### Rule 17 — Security

- Strict CSP (`default-src 'self'`). No external runtime sources — the zero-asset architecture makes this achievable, so do not undermine it by pulling in a CDN.
- No `eval`, no `Function` constructor, anywhere, including the PRNG.
- Validate and schema-check all `localStorage` input.
- `npm audit` clean. Exact-pinned versions. Lockfile committed.
- No secrets in the repository. There is no backend and no API key — if you think you need one, something has gone wrong.

### Rule 18 — Production readiness

Before any deploy:

- Production build succeeds with zero errors and zero warnings.
- Bundle ≤400 KB gzipped for the initial chunk. Report the actual size.
- Every §42 acceptance criterion verified.
- Tested in Chrome, Firefox, and Safari, plus one real mobile device.
- Debug overlays stripped.
- Security headers configured.
- **Open the deployed URL on a phone and actually play it.** That is where it will be judged.

## SUBSYSTEM IMPLEMENTATION NOTES

Specific guidance where the specification's intent could be misread.

### Physics core (Phase 2, spec §18–22)

Build in this order: fixed-timestep loop → tangent frame → gravity and drag → altitude PD → attitude control → camera.

The tangent-frame basis (§20.1) must be **re-orthonormalised every step.** Floating-point drift over thousands of steps skews the basis visibly within about a minute — this is not a theoretical concern.

Verify terminal velocity empirically against √(F/k) from §22.3. If it does not converge to 44.7 u/s at cruise, the drag integration is wrong, and every travel-time number in the design depends on it.

### Collision (Phase 4, spec §23)

Implement the analytic swept-sphere test in §23.2 **exactly as given.** Test it against the specific case that broke V1: a projectile at 220 u/s versus a 2.4 u target, where a naive per-frame distance check misses entirely.

Build brute-force collision first, verify it is correct, *then* add the bucket broadphase and assert the two produce identical results across 10,000 random configurations. Optimising before you have a correct reference gives you no way to tell whether the optimisation broke something.

### Rendering (Phase 5, spec §17)

Instance from the start. Retrofitting instancing is significantly more work than building with it.

The terrain worker (§33.2) must report genuine progress — the Loading screen's honesty depends on real stage callbacks, not a fake timer.

Verify the night-side readability resolution in §16.3 with an actual playtest. If emissive-only proves insufficient, add a subtle rim light. **Do not raise ambient** — that is precisely what V1 did (`game.js:1067`), and it flattened the entire lighting scheme.

### HUD (Phase 6, spec §14)

Build the **Threat Ring first.** It is the most novel component and the highest risk (R6). Prototype it early in the phase and test comprehension, rather than polishing it last.

Per-frame HUD values write to refs. Verify zero re-renders with the React profiler before moving on.

### Audio (Phase 7, spec §27)

All SFX synthesised — no sample files. Initialise the audio context only after a user gesture.

The lock tone's converging pitch interval *is* the progress indicator (§27.1). Get this right; it returns visual attention to flying, which is the whole point.

Verify the game is fully playable muted. Audio must never be the sole carrier of information.

## THE ONE THING TO REMEMBER

This game exists to create a single moment: two outposts are being drained on opposite sides of a moon, the player can only reach one, and they have to choose.

Everything else — the physics, the rendering, the audio, the HUD — exists to make that moment clear, fair, and tense.

When you are deciding how to implement something, ask whether it makes that moment better. If it does not, it probably should not be built.

Begin with Phase Zero: read `docs/gameplan.md`, inventory the repository, and report back before writing any code.
